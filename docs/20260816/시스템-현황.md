# hamster 시스템 현황 (20260816)

> 작성 기준: `main` @ `4e5f24e` / 코드 스캔 + 컴파일·타입체크 실행 결과.
> 대상 독자: 이 코드베이스에 처음 붙거나, 오랜만에 돌아와서 "지금 어디까지 됐나"를 30분 안에 잡아야 하는 사람.

---

## 0. 한 줄 결론

**hamster 는 "인증 1개 슬라이스만 실제로 완성된 UI 프로토타입"이다.** 화면(98개 TS/TSX)과 API 라우팅(30개 엔드포인트)은 넓게 깔려 있지만, 그 뒤의 도메인 로직은 대부분 `TODO()` 이거나 하드코딩 목데이터이고, 프론트가 부르는 URL 과 백엔드가 여는 URL 이 도서관 영역 전체에서 어긋나 있다.

**Why So** — 세 가지 측정치가 같은 방향을 가리킨다.

| 측정 | 값 | 의미 |
| --- | --- | --- |
| `TODO()` / `TBD` 를 포함한 백엔드 파일 | 14개 (도메인 서비스 8, 어댑터 4, DTO 매퍼 2) | 유스케이스 계약은 다 그렸는데 구현이 비어 있다 |
| DB 를 실제로 읽고 쓰는 경로 | `auth/*` (account·identity_link·refresh_token·auth_history) **뿐** | V1 마이그레이션의 도서관 8개 테이블은 런타임에 쓰이지 않는다 |
| 프론트가 호출하는 업무 API URL 중 백엔드에 실재하는 것 | 11개 중 **4개** (전부 place) | 도서관 화면 6개는 지금 붙여도 404 |

## 1. 시스템 지도

### 1-1. 런타임은 3개 컨테이너, 실행 앱은 1개

**So What** — 멀티모듈 6개지만 실제로 뜨는 프로세스는 `hamster-api` 하나다. 배포·디버깅 대상은 사실상 단일 앱으로 보면 된다.

```
브라우저 ─▶ hamster-front (nginx:80)  ─ /api ─▶ hamster-back (8080, 미노출) ─▶ postgres(library)
                SPA 서빙                  WebFlux + R2DBC            Flyway 는 JDBC 별도 커넥션
```

**Why So** — [infra/docker-compose.yml](../../infra/docker-compose.yml) 은 postgres / hamster-back / hamster-front 3서비스만 정의하고, 백엔드는 `expose` 만 하고 호스트 포트를 열지 않는다. `hamster-batch` 는 compose 에 없고 [HamsterBatchApplication.kt](../../hamster-back/hamster-batch/src/main/kotlin/com/hamsterbatch/HamsterBatchApplication.kt) 는 빈 스켈레톤이다.

### 1-2. 모듈 6개 중 컴포넌트 스캔 대상은 2개

| 모듈 | 상태 | 근거 |
| --- | --- | --- |
| `hamster-api` | ★ 실행 앱. 컨트롤러·어댑터·auth 전부 여기 | — |
| `library-core` | 활성. 유스케이스 계약 + 서비스(대부분 `TODO()`) | `scanBasePackages` 에 `com.librarycore` 포함 |
| `foundation` | 활성. 식별자·`CursorPage`·`UuidV7`. 스프링 무의존 | 유일하게 테스트가 있는 모듈(`IdGeneratorTest`) |
| `iam-core` | **죽어 있음.** `Admin.kt`/`User.kt` 2개, 스캔 제외 | [HamsterApiApplication.kt:10](../../hamster-back/hamster-api/src/main/kotlin/com/hamsterapi/HamsterApiApplication.kt#L10) 에서 주석 처리 |
| `place-core` | **빈 껍데기.** Kotlin 소스 0개 | `place-core/src` 에 `application.properties` 뿐 |
| `hamster-batch` | 스켈레톤. 잡 없음 | — |

**So What** — 문서상 "포트·어댑터, 코어는 스프링을 모른다"라고 되어 있지만 **현재 `library-core` 는 `spring-context` 에 의존하고 서비스에 `@Service` 가 붙어 있다.** 아키텍처 규칙이 이미 한 번 완화된 상태이므로, 새 코어 모듈을 만들 때 "스프링 무의존"을 전제로 설계하면 기존과 어긋난다. (근거: `library-core/build.gradle` 의 `implementation 'org.springframework:spring-context'`, 커밋 `f1ba755 feat : 코어모듈 스프링 의존성 추가`)

이 변경의 부작용으로 [ApplicationBeanConfig.kt](../../hamster-back/hamster-api/src/main/kotlin/com/hamsterapi/config/ApplicationBeanConfig.kt) 는 **파일 전체가 주석**이 되었다. 수동 `@Bean` 배선 → 컴포넌트 스캔으로 갈아탄 흔적이며, 지금은 순수 죽은 코드다.

## 2. 기능별 성숙도 — "돌아가는 것"과 "그려만 둔 것"

**So What** — 도메인 4개(auth / library / place / jira) 중 **end-to-end 로 실동작하는 것은 auth 하나뿐**이다. 나머지는 계층별로 어디까지 왔는지가 다르므로, 작업을 잡을 때 아래 표에서 "끊긴 지점"부터 보는 게 빠르다.

| 영역 | 화면 | 컨트롤러 | 유스케이스 | DB | 끊긴 지점 |
| --- | --- | --- | --- | --- | --- |
| **인증/RBAC** | ✅ | ✅ | ✅ | ✅ | — (유일한 완결 슬라이스) |
| **도서관** | ✅ 12화면 | ✅ 라우팅만 | ⛔ 대부분 `TODO()` | ⛔ 미연결 | 서비스 구현 + URL 계약 |
| **공간예약** | ✅ 6화면 | ⚠️ 하드코딩 응답 | ⛔ 모듈 자체가 빔 | ⛔ 테이블 없음 | 도메인·스키마 전부 |
| **지라** | ✅ 5화면 | ⛔ 없음 | ⛔ 없음 | ⛔ 없음 | 백엔드 전체 |

**Why So — 영역별 근거**

- **도서관:** 컨트롤러는 `book`/`loan`/`review` 3계열 모두 존재하지만, 뒤의 서비스가 [SearchBookService.kt](../../hamster-back/library-core/src/main/kotlin/com/librarycore/book/app/service/SearchBookService.kt) · [ReservationService.kt](../../hamster-back/library-core/src/main/kotlin/com/librarycore/book/app/service/ReservationService.kt) · [ReviewService.kt](../../hamster-back/library-core/src/main/kotlin/com/librarycore/review/ReviewService.kt) · [RankingService.kt](../../hamster-back/library-core/src/main/kotlin/com/librarycore/review/RankingService.kt) · [AdminLoanService.kt](../../hamster-back/library-core/src/main/kotlin/com/librarycore/loan/app/service/AdminLoanService.kt) 전부 `TODO("Not yet implemented")` 다. 즉 **호출하면 500**. 유일하게 응답을 돌려주는 건 [AdminBookService.kt:47](../../hamster-back/library-core/src/main/kotlin/com/librarycore/book/app/service/AdminBookService.kt#L47) 의 `listSkus` 인데, 이것도 companion object 에 박아둔 하드코딩 5권짜리 목록이다. DB 로 실제 쓰기가 일어나는 건 `register` 하나뿐.
- **공간예약:** [PlaceController.kt](../../hamster-back/hamster-api/src/main/kotlin/com/hamsterapi/place/api/PlaceController.kt) 와 [PlaceAdminController.kt](../../hamster-back/hamster-api/src/main/kotlin/com/hamsterapi/place/api/PlaceAdminController.kt) 가 companion object 의 `MOCK_*` 리스트를 그대로 반환한다. 서비스도 리포지토리도 없다. **역설적으로 프론트가 가장 잘 붙는 영역**인데, 목데이터가 백엔드에 있어서 응답 형태가 맞기 때문이다.
- **지라:** 프론트 전용. [jiraApi.ts](../../hamster-front/src/pages/jira/jiraApi.ts) 가 `MOCK_ISSUES` + 인위적 `delay()` 로 서버를 흉내 내고, 토큰을 `localStorage.getItem('auth_token')` 에서 읽는다 — **프로젝트의 인증 규칙(access token 은 메모리에만)과 정면으로 배치되는 별도 계통**이다.

## 3. 인증/인가 — 유일하게 믿을 수 있는 슬라이스, 단 인가는 아직 미적용

### 3-1. 흐름은 설계대로 완성돼 있다

```
SPA ─GET /api/v0/auth/login?redirect=&demo= ─▶ (302) IDP ─▶ GET /callback?code=&state=
   → AccountService.provision()  : IdentityLink 조회 → 없으면 ldapId 로 병합/신규생성 (JIT)
   → RefreshTokenService.issue() : 불투명 랜덤 32B, DB엔 SHA-256 만, family 부여
   → refresh 를 HttpOnly 쿠키(path=/api/v0/auth)로 심고 프론트 /auth/callback 으로 302
   → SPA 부트스트랩: POST /refresh → 회전 + access(JWT) 발급 → 메모리 보관
   → 업무 API: Authorization: Bearer, 401 이면 single-flight refresh 후 1회 재시도
```

**Why So** — [AuthController.kt](../../hamster-back/hamster-api/src/main/kotlin/com/hamsterapi/auth/api/AuthController.kt), [RefreshTokenService.kt](../../hamster-back/hamster-api/src/main/kotlin/com/hamsterapi/auth/iam/service/RefreshTokenService.kt)(회전 + 재사용 탐지 시 family 전체 폐기, `@Transactional`), [libraryClient.ts](../../hamster-front/src/core/http/libraryClient.ts)(`inflightRefresh` 로 중복 refresh 합치기)가 서로 맞물려 있다. 스키마도 [V2__create_auth.sql](../../hamster-back/hamster-api/src/main/resources/db/migration/V2__create_auth.sql) 로 정합.

설계상 좋은 판단 두 가지는 그대로 살아 있다.
- **경로 화이트리스트가 없다.** [JwtAuthWebFilter](../../hamster-back/hamster-api/src/main/kotlin/com/hamsterapi/auth/infra/jwt/JwtAuthWebFilter.kt) 는 토큰이 있으면 파싱만 하고 무조건 통과시키고, 보호는 `@AuthPrincipal` 파라미터를 선언한 핸들러에서만 401 로 걸린다. → 화이트리스트 관리 비용이 0. **대신 "보호는 opt-in"이라는 뜻이고, 이게 3-2 문제의 원인이다.**
- **IDP 는 어댑터 1개 교체로 갈아끼운다.** [IdpConfig](../../hamster-back/hamster-api/src/main/kotlin/com/hamsterapi/auth/idp/config/IdpConfig.kt) 가 `auth.idp` 로 Mock/SSO 를 고르고, **prod 프로파일에서 mock 이면 기동을 막는다**(설정 사고 방어). 이 가드는 실제로 들어가 있다.

### 3-2. 그런데 RBAC 은 "정의만 되어 있고 한 곳도 호출되지 않는다"

**So What** — `AdminAuthorization.verify()` 를 **호출하는 코드가 코드베이스에 단 한 줄도 없다.** 즉 현재 관리자 API 의 실질 보안 경계는 프론트 메뉴 게이팅뿐이고, 그건 보안 경계가 아니다.

**Why So** — 전체 grep 결과 `AdminAuthorization` 은 정의 파일([AdminAuthorization.kt](../../hamster-back/hamster-api/src/main/kotlin/com/hamsterapi/auth/support/AdminAuthorization.kt))과 예외를 잡는 [GlobalExceptionHandler](../../hamster-back/hamster-api/src/main/kotlin/com/hamsterapi/config/GlobalExceptionHandler.kt) 에만 등장한다. 관리자 컨트롤러의 인증 상태는 이렇다.

| 관리자 엔드포인트 | 인증(401) | 인가(403) |
| --- | --- | --- |
| `POST /api/v0/admin/library/books` | ✅ `@AuthPrincipal` | ⛔ 없음 — [AdminBookController.kt:38](../../hamster-back/hamster-api/src/main/kotlin/com/hamsterapi/book/api/AdminBookController.kt#L38) 은 `log.info(authInfo)` 만 한다 |
| `GET/PUT/DELETE /api/v0/admin/library/books/**` | ⛔ 없음 | ⛔ 없음 |
| `GET /api/v0/library/admin/loans/**` | ⛔ 없음 | ⛔ 없음 |
| `GET /api/v0/admin/places/**` | ⛔ 없음 | ⛔ 없음 |

또한 `GNB_NAV_ITEMS` 의 어떤 항목에도 `roles` 가 지정돼 있지 않다([navigation.config.tsx](../../hamster-front/src/app/gnb/navigation.config.tsx)). `canAccessNav` 와 `RequireAuth roles={...}` 는 구현돼 있지만 **아무도 쓰지 않는다** — 로그인만 하면 전 메뉴가 보인다. 결국 `USER` / `MANAGER` / `SUPER_ADMIN` 3역할은 지금 토큰에만 실려 다니고 아무 것도 막지 않는다.

## 4. 지금 손대면 바로 걸리는 함정 5가지

우선순위 순. 전부 파일 근거를 붙인다.

### ① `/refresh` 는 매 호출마다 auth_history INSERT 를 한다 — 그리고 미구현 메서드 2개가 같은 어댑터에 있다

**So What** — access token 발급 경로가 DB 쓰기에 묶여 있다. "무상태 JWT" 라는 주석과 달리 발급은 상태를 남기며, DB 장애 = 로그인 전면 불가다. 나중에 토큰 블랙리스트를 켜려고 `blockToken`/`isBlocked` 를 호출하는 순간 `NotImplementedError` → 500 이 난다.

**Why So** — [JwtService.kt:50](../../hamster-back/hamster-api/src/main/kotlin/com/hamsterapi/auth/iam/service/JwtService.kt#L50) 이 `authHistoryOutPort.saveHistory(...)` 를 무조건 호출하고, 같은 포트의 [AuthHistoryOutPersistenceAdapter.kt:19,23](../../hamster-back/hamster-api/src/main/kotlin/com/hamsterapi/auth/infra/persistance/AuthHistoryOutPersistenceAdapter.kt#L19) 은 `TODO()` 다. `BlockedTokenEntity`/`BlockedTokenRepository` 도 정의만 되어 있고 참조하는 코드가 없다(테이블도 마이그레이션에 없다).

### ② 프론트–백엔드 URL 계약이 도서관 영역 전체에서 어긋나 있다

**So What** — 도서관 화면은 "붙였는데 데이터가 안 나온다"가 아니라 **애초에 404** 다. 화면 디버깅 전에 URL 표부터 맞춰야 한다.

**Why So** — 프론트 호출 vs 백엔드 매핑 대조:

| 프론트가 부르는 URL | 백엔드 실제 경로 | 판정 |
| --- | --- | --- |
| `/api/v0/admin/books/sku` | `/api/v0/admin/library/books` | ❌ |
| `/api/v0/admin/books/loans` | `/api/v0/library/admin/loans/loans` | ❌ |
| `/api/v0/admin/books/overdue` | `/api/v0/library/admin/loans/overdue` | ❌ |
| `/api/v0/admin/books/reservations` | `/api/v0/admin/library/books/reservations` | ❌ |
| `/api/v0/admin/library/books/ratings` | (없음) | ❌ |
| `/api/v0/library/books/rankings` | `/api/v0/library/review` | ❌ |
| `/api/v0/admin/places/room-resources` | `/api/v0/admin/places/room-resource` (단수) | ❌ |
| `/api/v0/places/dashboard`, `/buildings`, `/api/v0/admin/places/rooms`, `/reservations` | 동일 | ✅ |

백엔드 자체 네이밍도 갈라져 있다: 관리자 도서는 `/admin/library/books`, 관리자 대출은 `/library/admin/loans`. **접두사 규칙(`/admin/{domain}` vs `/{domain}/admin`)을 먼저 하나로 정하지 않으면 고쳐도 또 어긋난다.**

추가로 [PlaceController.kt:52](../../hamster-back/hamster-api/src/main/kotlin/com/hamsterapi/place/api/PlaceController.kt#L52) 는 클래스 `@RequestMapping("/api/v0/places")` 아래에 `@GetMapping("/places/{roomId}/reservations")` 를 달아 실제 경로가 `/api/v0/places/places/{roomId}/reservations` 다 — 바로 위 주석([:18](../../hamster-back/hamster-api/src/main/kotlin/com/hamsterapi/place/api/PlaceController.kt#L18))이 적어둔 의도와 다르다.

### ③ 예외 핸들러의 Enum 분기는 Spring Boot 4 에서 죽은 코드다

**So What** — 잘못된 enum 값을 보내도 "허용 가능한 값" 안내가 나가지 않고 일반 400 으로 떨어진다.

**Why So** — [GlobalExceptionHandler.kt:3](../../hamster-back/hamster-api/src/main/kotlin/com/hamsterapi/config/GlobalExceptionHandler.kt#L3) 이 `com.fasterxml.jackson.databind.exc.InvalidFormatException`(Jackson 2)을 import 하는데, 이 앱의 JSON 스택은 `tools.jackson.module:jackson-module-kotlin`(Jackson 3)이다([hamster-api/build.gradle](../../hamster-back/hamster-api/build.gradle), `IdpConfig` 도 `tools.jackson.databind.ObjectMapper` 를 주입받는다). Jackson 2 는 `jjwt-jackson` 이 끌고 와서 **컴파일은 통과하지만 런타임에 그 타입으로 던져지지 않는다.**

### ④ 패키지 선언과 디렉터리가 어긋난 파일이 6개

**So What** — `book/infra/persistence/` 에 있는데 패키지는 `com.hamsterapi.book.app.jpa` 다. IDE 탐색과 grep 이 서로 다른 답을 주고, 이미 사라진 JPA 시절 네이밍(`jpa`)이 R2DBC 코드에 남아 있다.

**Why So** — `BookSkuMasterRecord` / `BookInventoryDetailRecord` / `BookRatingRecord` / `BookReservationRecord` / `LoanMasterRecord` / `LoanDetailRecord` / `LoanOverdueRecord` 가 `package com.hamsterapi.book.app.jpa`. 같은 디렉터리의 Repository 2개만 `...book.infra.persistence` 로 올바르다. (참고로 auth 쪽은 디렉터리명이 `persistance` 오타지만 패키지와는 일치한다.)

### ⑤ 남은 디버그 잔재

[BookPersistenceAdapter.kt:14](../../hamster-back/hamster-api/src/main/kotlin/com/hamsterapi/book/app/BookPersistenceAdapter.kt#L14) 의 `println(bookSku.toString())`, [AdminBookController.kt:38](../../hamster-back/hamster-api/src/main/kotlin/com/hamsterapi/book/api/AdminBookController.kt#L38) 의 `log.info(authInfo.toString())`(인증 주체 전체를 INFO 로 덤프 — email·roles 포함). 프론트에는 `ProtectedRoute`/`pages/auth/useAuth.ts` 같은 **호환용 재노출 래퍼**와, `main.tsx` 가 쓰지 않는 [AppRoutes.tsx](../../hamster-front/src/app/AppRoutes.tsx)(주석에 "참고용"이라 명시)가 남아 있다.

## 5. 검증 현황

**So What** — 컴파일·타입체크는 통과하지만, 그것이 "동작한다"의 근거는 아니다. 테스트가 사실상 없기 때문에 위 ①~③ 같은 런타임 결함은 빌드로 걸러지지 않는다.

**Why So** — 실행 결과:

| 검증 | 명령 | 결과 |
| --- | --- | --- |
| 백엔드 컴파일 | `JAVA_HOME=$(/usr/libexec/java_home -v 21) ./gradlew :hamster-api:compileKotlin` | ✅ exit 0 |
| 프론트 타입체크 | `./node_modules/.bin/tsc --noEmit` | ✅ exit 0 |
| 테스트 | — | 전 모듈 통틀어 `IdGeneratorTest` 1개 + 빈 `HamsterBatchApplicationTests` |

린트/포맷 태스크(spotless·ktlint)는 백엔드에 없고, 프론트는 `npm run lint` 만 있다.

## 6. 다음에 손댈 순서 (제안)

**So What** — "기능 추가"보다 **계약 정리가 먼저**다. 지금 기능을 얹으면 어긋난 URL·미적용 인가 위에 쌓게 된다.

1. **API 경로 규칙 확정 → 프론트/백엔드 동시 정정** (②). 표 8행이 근거이자 체크리스트. 규칙 하나 정하면 기계적 작업이다.
2. **`AdminAuthorization.verify()` 를 관리자 컨트롤러에 실제로 붙이기** (3-2). 인가 코드는 이미 다 있고, 호출과 `@AuthPrincipal` 파라미터만 없다. 동시에 `GNB_NAV_ITEMS` 에 `roles` 를 채워 UX 를 맞춘다.
3. **도서관 수직 슬라이스 1개를 끝까지 뚫기** (예: 자료검색 `SearchBookService`). 컨트롤러–서비스–어댑터–V1 테이블 경로를 한 번 완주해야 나머지 `TODO()` 들의 복제 기준이 생긴다.
4. **auth_history 발급 기록을 비동기/선택적으로 분리** (①). 최소한 `blockToken`/`isBlocked` 는 쓰지 않을 거면 포트에서 지우고, 쓸 거면 테이블부터 만든다.
5. **공간예약: 목 컨트롤러를 `place-core` + 스키마로 승격** (③이 아니라 ②·③ 정리 후). 프론트가 이미 붙어 있어 응답 계약은 확정돼 있으니 역방향으로 도메인을 채우면 된다.
