# R2DBC ↔ JPA 스위치 — 설계 변경대응력 실험 기록

**작성일:** 2026-08-16
**목적:** 성능 비교가 아니다. R2DBC 학습과, 현재 포트·어댑터 설계가 영속성 교체를 실제로 흡수하는지 확인하는 것이다.
**결과:** 흡수했다. 단, 비용은 예상한 곳에 없었다.

---

## 1. 결론

**설계는 통과했다. 도메인·유스케이스·컨트롤러를 한 글자도 고치지 않고 영속성 구현을 통째로 갈아끼웠다.**

`--spring.profiles.active=local` 이면 R2DBC, `local,jpa` 면 JPA 다. 같은 엔드포인트(`POST /api/v0/admin/library/books`)를 양쪽에서 실행한 결과가 동일하다.

| 모드 | 부팅 | HTTP | book_sku_master | book_inventory_detail | 실행 스레드 |
| --- | --- | --- | --- | --- | --- |
| 기본 (R2DBC) | 1.302s | 200 | 1건 | 3건 AVAILABLE | reactor-netty |
| `jpa` | 2.031s | 200 | 1건 | 3건 AVAILABLE | `virtual-65` |

**그런데 진짜 비용은 어댑터를 두 벌 쓰는 데 있지 않았다. 스프링이 두 스택의 공존 자체를 막고 있는 지점 세 곳에 있었다.** 어댑터 작성은 기계적이었고, 시간을 쓴 곳은 전부 오토컨피그와 트랜잭션 매니저였다. 이 문서의 본론은 3절이다.

---

## 2. 왜 코어를 안 고쳐도 됐나

**포트가 이미 `suspend` 로 선언돼 있었기 때문이다.**

```kotlin
// library-core — 이번 작업에서 변경 없음
interface BookOutPort {
    suspend fun saveSku(bookSku: BookSku)
}
```

`suspend` 는 리액티브 전용 시그니처가 아니라 **양쪽 다 구현할 수 있는 중립 계약**이다. 이 성질 덕분에 두 구현이 같은 인터페이스에 그대로 들어맞았다.

- R2DBC 구현: 코루틴 리포지토리를 그대로 호출
- JPA 구현: `withContext(버추얼스레드 디스패처) { 블로킹 호출 }`

만약 포트가 `Mono<Void>` 였다면 JPA 구현은 계약을 만족시키려고 `Mono.fromCallable` 로 감싸는 껍데기를 써야 했고, 그 타입이 `library-core` 전체에 리액터 의존을 퍼뜨렸을 것이다. **코어에 리액티브 타입을 노출하지 않은 판단이 여기서 값을 했다.**

추가로 확인된 사실: `library-core` 는 스프링 컨텍스트에 `@Service` 로 올라가지만 DB 기술은 전혀 모른다. 컨트롤러도 `suspend fun` 만 쓰고 있어 웹 계층 역시 무관했다.

## 3. 실제로 막힌 세 곳 — 이번 실험의 본론

계획 단계에서는 하나도 안 보였고, 셋 다 **부팅하거나 요청을 태워야만** 드러났다.

### 3.1 Boot 는 R2DBC 를 감지하면 DataSource 오토컨피그를 통째로 끈다

**`spring.datasource.url` 을 아무리 정확히 넣어도 DataSource 가 만들어지지 않는다.** 설정 실수가 아니라 Boot 의 의도다.

`--debug` condition 리포트 원문:

```
DataSourceAutoConfiguration:
   Did not match:
      - @ConditionalOnMissingBean (types: io.r2dbc.spi.ConnectionFactory; SearchStrategy: all)
        found beans of type 'io.r2dbc.spi.ConnectionFactory' connectionFactory (OnBeanCondition)
```

"리액티브를 선택했으면 블로킹 DataSource 는 만들지 않는다"는 방침이 조건에 박혀 있다. 그 연쇄로 `HibernateJpaAutoConfiguration` 도 DataSource 를 못 찾아 EntityManagerFactory 가 안 생기고, 최종적으로 이렇게 터진다.

```
Parameter 0 of constructor in JpaBookWriter required a bean named
'entityManagerFactory' that could not be found.
```

**대응:** `JpaPersistenceConfig` 에서 DataSource 를 손으로 등록한다. Boot 의 표준 수동 패턴을 그대로 쓰되, 오토컨피그가 꺼져 있으므로 `DataSourceProperties` 도 직접 올려야 한다.

```kotlin
@Bean
@ConfigurationProperties("spring.datasource")
fun jpaDataSourceProperties(): DataSourceProperties = DataSourceProperties()

@Bean
@ConfigurationProperties("spring.datasource.hikari")
fun dataSource(properties: DataSourceProperties): HikariDataSource =
    properties.initializeDataSourceBuilder().type(HikariDataSource::class.java).build()
```

> **함의:** R2DBC 를 쓰는 앱에 JPA 를 얹는 구성은 스프링이 지원하는 경로가 아니다. 점진적 마이그레이션을 하려면 이 수동 배선을 계속 떠안아야 한다.

### 3.2 트랜잭션 매니저가 둘이 되면 기존 인증이 깨진다

**JPA 를 켜는 순간, JPA 와 무관한 `RefreshTokenService.rotate` 가 부팅 후 첫 로그인에서 죽는다.**

`@Transactional` 에 한정자가 없으면 스프링은 `TransactionManager` 타입 빈을 유일하게 찾아야 한다. `R2dbcTransactionManager` + `JpaTransactionManager` 가 공존하면 `NoUniqueBeanDefinitionException` 이다. 기존 코드는 전부 리액티브이므로 **R2DBC 쪽을 기본값으로 못박는 게 맞다.**

```kotlin
@Bean
@Primary   // 빈 이름을 오토컨피그와 동일하게 두어 중복 등록도 피한다
fun connectionFactoryTransactionManager(cf: ConnectionFactory): ReactiveTransactionManager =
    R2dbcTransactionManager(cf)

@Bean
fun jpaTransactionManager(emf: EntityManagerFactory): PlatformTransactionManager =
    JpaTransactionManager(emf)
```

JPA 쪽은 이름으로만 지정해 쓴다. **auth 코드는 건드리지 않았다** — 이게 중요하다. 새 스택을 얹으면서 기존 스택 코드를 수정해야 했다면 그건 설계가 진 것이다.

### 3.3 Spring Data JPA 리포지토리는 기본 이름 `transactionManager` 를 찾는다

**컴파일도 부팅도 통과하고, 요청을 태워야 500 으로 나타난다.** 세 함정 중 제일 늦게 드러난다.

```
No bean named 'transactionManager' available:
No matching TransactionManager bean found for qualifier 'transactionManager'
```

`SimpleJpaRepository` 자체가 `@Transactional` 이고, `@EnableJpaRepositories.transactionManagerRef` 의 기본값이 `"transactionManager"` 다. 3.2 에서 그 이름을 안 쓰기로 했으니 참조를 명시해야 한다.

```kotlin
@EnableJpaRepositories(
    basePackages = ["com.hamsterapi.book.infra.persistence.jpa"],
    transactionManagerRef = "jpaTransactionManager",
)
```

> **교훈:** 트랜잭션 매니저 이름을 기본값에서 벗어나게 하는 순간, 그 이름에 암묵적으로 의존하던 프레임워크 코드가 전부 깨진다. 그리고 그 대부분은 정적 검증에 안 걸린다.

## 4. 구조

```
book/infra/persistence/
├── r2dbc/
│   ├── BookSkuMasterRecord · BookInventoryDetailRecord · (+ Reservation/Loan/Rating)
│   ├── BookSkuMasterRepository · BookInventoryDetailRepository · BookReservationRepository
│   └── R2dbcBookPersistenceAdapter          @Profile("!jpa")
└── jpa/
    ├── BookSkuMasterEntity · BookInventoryDetailEntity
    ├── BookSkuMasterJpaRepository
    ├── JpaBookWriter                        @Transactional("jpaTransactionManager")
    └── JpaBookPersistenceAdapter            @Profile("jpa")

config/
├── R2dbcPersistenceConfig    스캔 범위 명시
└── JpaPersistenceConfig      @Profile("jpa") — DataSource·트랜잭션매니저·디스패처
```

**패키지 분리는 취향이 아니라 필수였다.** 기존 R2DBC Record 들이 `package com.hamsterapi.book.app.jpa` 로 선언돼 있었고(디렉터리는 `infra/persistence`), 진짜 JPA 엔티티가 생기면서 이름이 정면 충돌했다. `r2dbc/` 로 정정하면서 패키지와 디렉터리도 일치시켰다.

`R2dbcPersistenceConfig` 로 스캔 범위를 명시한 이유: Spring Data 모듈이 둘이 되면 같은 리포지토리 인터페이스를 서로 자기 것이라 주장할 여지가 생긴다. 자동 판별에 기대지 않고 못박았다.

```kotlin
@EnableR2dbcRepositories(basePackages = [
    "com.hamsterapi.auth.infra.persistance",
    "com.hamsterapi.book.infra.persistence.r2dbc",
])
```

## 5. R2DBC vs JPA — 같은 `saveSku` 한 개에서 갈리는 지점

**대비가 제일 선명한 곳은 부모-자식 저장이다. R2DBC 에는 cascade 가 없다.**

**R2DBC** — 부모를 저장해 채번된 id 를 받아 자식을 직접 넣는다:

```kotlin
@Transactional
override suspend fun saveSku(bookSku: BookSku) {
    val savedSku = skuRepository.save(BookSkuMasterRecord.from(bookSku))
    val skuId = checkNotNull(savedSku.id) { "book_sku_master 채번 실패" }
    inventoryRepository.saveAll(bookSku.inventories.map { ... }).collect()
}
```

**JPA** — `cascade = ALL` 이 자식 insert 와 FK 세팅을 대신한다:

```kotlin
@Transactional("jpaTransactionManager")
fun saveSku(bookSku: BookSku) {
    skuRepository.save(BookSkuMasterEntity.from(bookSku))   // 이게 전부
}
```

실제 발행 SQL (Hibernate 로그, 수량 3 기준):

```
insert into book_sku_master (author, available_copies, ..., total_copies, updated_at)
insert into book_inventory_detail (book_sku_id, created_at, status)
insert into book_inventory_detail (book_sku_id, created_at, status)
insert into book_inventory_detail (book_sku_id, created_at, status)
```

**주의할 비대칭:** JPA 는 자식 3건을 개별 insert 로 쏜다(배치 미설정). R2DBC 구현은 `saveAll` 을 쓰지만 이 역시 건별 insert 다. 즉 지금은 발행 SQL 이 우연히 같지만, **JPA 에 배치나 지연로딩이 끼기 시작하면 두 구현의 쿼리 프로파일이 갈라진다.** 나중에 수치를 볼 일이 생기면 발행 SQL 부터 맞춰야 한다.

### 블로킹 경계

JDBC 는 블로킹이므로 이벤트 루프에서 내보내야 한다. **그 경계를 감추지 않고 한 줄로 드러냈다.**

```kotlin
override suspend fun saveSku(bookSku: BookSku) = withContext(dispatcher) {
    writer.saveSku(bookSku)
}
```

`JpaBookWriter` 를 어댑터에서 분리한 이유 두 가지:

1. **`suspend` 함수에 `@Transactional` 을 걸면 스프링이 리액티브 트랜잭션으로 해석해 `ReactiveTransactionManager` 를 찾는다.** JPA 는 `PlatformTransactionManager` 라 맞지 않는다.
2. 자기 호출(self-invocation)은 프록시를 안 타서 `@Transactional` 이 먹지 않는다.

디스패처는 버추얼 스레드다. 실행 로그에서 `[virtual-65]` 로 확인했다. 다만 **실제 동시성 상한은 디스패처가 아니라 Hikari 풀 크기가 정한다** — 버추얼 스레드는 무제한이어도 커넥션은 10개다.

## 6. 부수적으로 드러난 것

**`BookInventoryDetailRecord` 가 스키마와 안 맞아 있었다.** 미사용이라 안 터지고 있었을 뿐이다.

- `@Id val pk` → `book_inventory_detail` 에 `pk` 컬럼 없음 (실제는 `id`)
- `val bookInventoryId: BookInventoryId` → `book_inventory_id` 컬럼 자체가 없음

V1 스키마 기준으로 맞췄다. Hibernate `ddl-auto: validate` 로 JPA 쪽 매핑은 부팅 시 자동 검증되지만, **R2DBC 에는 이런 검증이 없다** — 이 불일치가 오래 숨어 있었던 이유다.

**미해결로 남긴 것:** 도메인 `BookSkuId`/`BookInventoryId` 는 UUID 인데 DB 는 BIGINT 채번이다. 대응 컬럼이 없어 저장 시 도메인 식별자가 버려진다. 별개 설계 이슈라 이번에 건드리지 않았다.

## 7. 범위와 한계

- **JPA 로 바뀌는 건 `BookOutPort` 하나뿐이다.** auth 리포지토리 5개는 `jpa` 프로파일에서도 R2DBC 그대로다. 오히려 이게 두 스택 공존을 증명한다 — jpa 모드에서 로그인(리액티브 트랜잭션 경로)이 정상 동작했다.
- **성능 수치는 측정하지 않았다.** 이 실험의 목적이 아니고, 지금 구성으로 잰 숫자는 의미가 없다. 재려면 풀 크기 정렬, 발행 SQL 일치, open model 부하, JDK 21 의 버추얼스레드 핀닝(`-Djdk.tracePinnedThreads`) 확인이 선행돼야 한다.
- **테스트 코드는 없다.** 검증은 `:hamster-api:build` + 두 프로파일 부팅 + API 실행 + DB 직접 확인으로 했다.
- 로컬 DB 에 테스트 도서 2건(`9791100000001`, `9791100000002`)이 남아 있다.

## 8. 실행 방법

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 21)

# R2DBC (기본)
./gradlew :hamster-api:bootRun --args='--spring.profiles.active=local'

# JPA + 버추얼 스레드
./gradlew :hamster-api:bootRun --args='--spring.profiles.active=local,jpa'
```

`jpa` 는 환경 프로파일에 얹는 **오버레이**다. 단독으로 쓰지 않는다. 이 프로파일이 없으면 JDBC DataSource 가 없어 JPA 관련 빈이 하나도 생성되지 않으므로, **기본 경로에는 어떤 영향도 없다.**
